Tool-agent-user interaction and conversational service agents

These benchmarks test service agents in multi-turn conversations. The agent must collect information, use tools, and follow a domain policy.

Key points

  • Task success depends on the final result, not on a fixed dialogue script.
  • passk measures whether an agent succeeds in every repeated trial.
  • Active users, multimodal inputs, and ambiguous policies add separate sources of difficulty.
  • The benchmarks use simulated users. Simulator errors can affect the measured agent score.

What the setting tests

Yao et al. (2024) define the base setting in τ-bench. An agent talks with a simulated user and calls domain APIs. The agent also receives a policy document.

The user has a private task instruction. The agent must ask for the information that it needs. The agent cannot see the database directly. It reads or changes the database through tools.

τ-bench checks two outputs. First, it compares the final database state with an annotated goal state. Second, it checks whether the agent gave the required information to the user. The authors note that this rule-based check can miss some policy violations, such as action without required user confirmation.

How the benchmarks extend the setting

τ-bench: conversation, tools, and rules

τ-bench contains retail and airline tasks. GPT-4o with function calling reached 61.2% pass1 in retail and 35.2% in airline. Its retail pass8 was about 25%. These results show a large gap between one successful trial and repeated success.

passk is different from pass@k. Pass@k asks whether at least one of k trials succeeds. passk asks whether all k trials succeed.

τ²-bench: the user can act

Barres et al. (2025) add a telecom setting in which both parties can use tools. For example, the agent can inspect support data while the user changes phone settings. The task therefore requires communication and coordinated action.

The authors compare full dual control with a no-user condition. They report a decrease of about 20 percentage points in pass1 when the agent must guide a user. This ablation supports their conclusion that communication and coordination cause distinct failures.

User simulation remains a measurement risk. In the authors’ manual sample, the telecom simulator had a 16% total error rate. The inherited retail and airline simulators had error rates of 40% and 47%. The samples were small, and only some errors made a task impossible to complete.

ECom-Bench: multimodal support and personas

Wang et al. (2025) focus on e-commerce support. Their tasks include text and image inputs. The simulated users have persona data based on e-commerce customer interactions.

GPT-4o reached 44.03% pass1 and 16.98% pass3. In the reported architecture comparison, GPT-4o used a multimodal model as a tool and scored higher than two end-to-end multimodal planners. This comparison covers different models as well as different architectures, so it does not isolate architecture alone.

DRIP-R: ambiguous policy

Borkakoty et al. (2026) study return policies that allow more than one valid interpretation. DRIP-R uses 40 return tasks and 10 customer personas, for 400 scenarios. The authors derived the tasks from one Amazon return-policy document.

The four tested models gave the same resolution in 4.2% of scenarios. They gave four different resolutions in 13.3%. The other 82.4% had partial agreement. These figures measure agreement, not correctness, because the benchmark is designed around policy ambiguity.

The customer simulator is stochastic. The authors state that it contributes to measured variation. They leave agent-only variance, based on fixed customer turns, for future work.

What the evidence supports

  • Repeated success is difficult. τ-bench and ECom-Bench report large score decreases as k increases.
  • User action adds difficulty. τ²-bench reports lower performance when the agent must guide an active user.
  • The simulator is part of the test. A simulator can omit a constraint, stop too early, or add unsupported details.
  • Policy design changes the meaning of success. τ-bench creates tasks with one intended outcome. DRIP-R creates tasks that can have several valid outcomes.
  • Results do not transfer automatically across benchmarks. The domains, tools, models, user simulators, and scoring methods differ.

Papers in this field

  • Yao et al. (2024). τ-bench tests multi-turn tool use, policy use, and repeated reliability in retail and airline tasks.
  • Barres et al. (2025). τ²-bench gives tools to both the agent and the simulated user in a telecom support environment.
  • Wang et al. (2025). ECom-Bench adds e-commerce personas, image-based tasks, and multimodal tools.
  • Borkakoty et al. (2026). DRIP-R tests decisions when a retail policy supports several interpretations.

A key difference in benchmark design

τ-bench creates each task so that the policy and user request lead to one goal state. It can then score the final database state against that goal.

DRIP-R starts with ambiguous policy clauses. It does not assume that every scenario has one correct resolution. It uses several evaluation dimensions and reports model agreement.

These designs answer different questions. A low τ-bench score shows failure against its annotated goal. Disagreement in DRIP-R shows resolution instability under its ambiguous policies. The current studies do not show how much ambiguity explains failures in τ-bench.

Open questions

  • How should researchers separate agent failures from user-simulator failures?
  • How can benchmarks test expert-to-novice guidance without assuming that users share the agent’s mental model?
  • Can domain and policy construction scale without extensive manual work?
  • Do results generalize beyond the current retail, airline, telecom, and home-appliance settings?
  • How should a benchmark score a valid decision when a policy permits several outcomes?
  • How can persona design use stronger behavioral evidence and avoid unfair differences in service outcomes?

These questions come from the limitations and future-work sections of the cited papers. See the wiki’s Open Questions page for the wider list.
