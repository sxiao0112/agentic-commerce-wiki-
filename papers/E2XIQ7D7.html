ECom-Bench: Can an LLM agent resolve real-world e-commerce support issues?

A compact technical reading of a benchmark for multi-turn customer support, tool use, database changes, and image understanding.

  • Wang et al.
  • EMNLP 2025 main conference
  • arXiv:2507.05639v2
  • 9 Nov 2025
  • Wiki ID: E2XIQ7D7

Pinned record · Primary full text · Code and data

Research question

How reliably can an LLM agent complete realistic e-commerce support tasks when it must converse with a simulated customer, follow domain rules, call tools, change database state, and sometimes interpret an image?

The paper treats reliability as repeated success on the same task. A model that succeeds once but fails on a repeat is less useful for customer support. This choice drives the benchmark’s passk metric. Primary source: §1 and §3.

Task and environment

53manually verified tasks
18tasks with multimodal interaction
21tool categories
3rule-check dimensions

What the agent receives

Domain operation documents and a tool interface over product, logistics, order, invoice, return, exchange, and related records. An image-processing tool supports multimodal tasks.

Who plays the customer

Qwen-Max simulates a user from a persona and a task goal. Persona fields cover consumer type, emotion, attention, patience, trust, rights awareness, question style, communication style, and interaction pattern.

Where tasks come from

Trained customer-service staff extracted customer intents from historical online dialogues. LLMs generated preliminary benchmark data, and humans reviewed it. The source domain is mainly home appliances and furniture.

What counts as evidence

The evaluator checks the final database state, whether required retrieval tools were called, and whether the final output contains required keywords. These are rule checks, not a model judge.

Primary source: §3, Benchmark Construction.

One evaluation trajectory

  1. Select task and personaInput: one task goal, database state, user guide, and persona.
  2. Start the dialogueQwen-Max acts as the customer. The tested model acts as support agent.
  3. Reason and use toolsThe agent follows ReAct, calls MCP tools, and can ask the image tool for visual content.
  4. Apply three rule checksCompare database state; check required retrieval calls; check required output keywords.
  5. Repeat and aggregateRun the task independently and report the share of all-success run subsets as passk.

Metric: passk measures repeated success

For one task, let n be the number of independent trials and c the number that succeed. For a chosen k, the paper uses:

passk = Etask[ C(c, k) / C(n, k) ]
Numerator C(c,k)
The number of size-k subsets in which every selected run succeeded.
Denominator C(n,k)
All size-k subsets available from the task’s n runs.
Outer average
The mean of that ratio across benchmark tasks. A result such as 16.98 is a percentage: 16.98%.
Task denominator
The main benchmark average covers 53 tasks; the persona study covers 20 selected tasks. The eight-run analysis states n = 8. The paper does not state n explicitly for Table 2 in its setup text.
passk: all k runs succeedC(c,k) / C(n,k). The score falls as repeated reliability becomes harder.
pass@k: at least one of k runs succeeds1 − C(n−c,k) / C(n,k). This common code-generation metric answers a different question and usually rises with k.

Formula and interpretation: §3, Evaluation and §4. The pass@k formula is shown only to clarify the name; it is not an ECom-Bench result.

What the results establish

Single-run success stays below half

GPT-4o leads Table 2 at 44.03% pass1. No tested model resolves a majority of tasks in a single run under this setup.

Reliability falls sharply

In the eight-run analysis, GPT-4o records 43.87% pass1 and 7.55% pass8. Only a small share of tasks succeed in every one of eight runs.

Actions are the weakest dimension

The paper reports higher failure rates for database-changing actions than for search or output checks across all agents.

Wrong decisions dominate one error sample

For 159 Doubao-1.5-Pro-32k trajectories (53 tasks × 3), the paper groups failures as wrong argument, wrong decision, or partially resolved, and reports wrong decision as most common.

Reading: The gap between pass1 and passk exposes operational variance that one-shot accuracy hides. For deployment, a support agent must execute the full workflow correctly each time, including state changes.

Primary source: §4.2.3, §4.2.4, and §4.2.5.

Limits and interpretation boundaries

  • Narrow domain: the benchmark covers home appliances and furniture. Cross-category generalization is untested.
  • Partly synthetic data: commercial-data sensitivity led to LLM-based synthesis. Human review does not make the data fully authentic.
  • Small environment: 53 tasks and a relatively small database with simplified operations limit coverage.
  • Simulated users: persona dimensions rely mainly on domain expertise and lack sufficient theoretical validation and empirical analysis. LLM behavior may miss real conversational dynamics.
  • Selected persona subset: the persona experiment uses 20 tasks chosen for sensitivity to persona settings. It does not estimate an average effect over all 53 tasks.
  • Architecture comparison is confounded: the decoupled system uses GPT-4o plus Moonshot-V1-128k-Vision-Preview, while the end-to-end planners are different model families. The observed difference cannot isolate architecture from model capability.
  • Incomplete reproducibility detail: the paper gives model names and shared runtime settings, but not model snapshot IDs, full prompts, uncertainty intervals, or significance tests.
  • Binary success rule is underspecified: the paper names the three rule-check dimensions, but its prose does not formally state how those checks combine into one successful or failed trial.
Do not read 16.98% pass3 as pass@3. It estimates success in all three selected runs, averaged over tasks. It does not mean that one of three attempts succeeds 16.98% of the time.

Author-stated limitations: Limitations. The selected-subset and architecture-confound points are direct methodological readings of §5.1 and §4.2.2.
